# 租赁售卖平台：痛点与优化方案

本方案以“同一类资产可以出租，也可以销售”为前提，适用于设备、车辆、工具、活动物料、房源等按数量管理的场景。痛点按资产、交易、履约、风控和经营五个环节梳理。

## P0：首版必须解决

| 痛点 | 业务后果 | 本版优化 | 后续加强 |
| --- | --- | --- | --- |
| 同一库存被售出又被未来租出；热门日期超租 | 到店无货、赔付、客服冲突 | `products` 与 `inventory_commitments` 分离；租赁按 `daterange` 占用；订单事务按商品 ID 顺序 `FOR UPDATE` 加锁并计算区间峰值 | 按门店建立库存池；逐件资产使用二维码 / SN 与排他约束 |
| 商品改价后订单金额说不清 | 客户质疑临时加价、财务难对账 | 订单行保存 SKU、名称、售价、日租金、押金和小计快照 | 价格规则版本、优惠、税费、报价单版本化 |
| 押金、租金和退款混在一个订单金额里 | 漏退、重复收款、无法解释资金差异 | 金额以分保存；`payments` 单独记录收款 / 退款；订单汇总已收金额和状态 | 支付回调幂等键、押金预授权、退款审批和账本对账 |
| 人工改库存破坏已确认租约 | 未来订单无法履约 | 库存调整前计算未来租赁峰值；若调整后库存不足则拒绝 | 入库、报损、维修、调拨都走不可变库存流水和审批 |
| 取货、归还与取消没有闭环 | 资产长期被错误占用或被重复出售 | 租赁状态机、交接日期约束、归还 / 取消释放承诺；销售取消恢复库存 | 部分交接、续租、逾期冻结、异常替代品调拨 |

## P1：先做风控和履约证据

| 痛点 | 方案 |
| --- | --- |
| 设备状态与损坏责任说不清 | 取货和归还强制扫码；生成带操作人、时间戳、照片、配件清单和双方确认的验机单；不合格资产自动转维修。 |
| 未付款订单长期占库存 | 增加 `pending_payment`、`expires_at` 和后台释放任务；支付确认采用幂等键。 |
| 假商家、身份冒用、逾期不还 | 商家主体 / 收款账户 / 资产所有权核验；高价值租赁分级实名认证；站内支付、交接 OTP、异常频次与黑名单规则。 |
| 多门店调拨、配送取还靠人工 | 建立“商品 × 门店”库存池、配送 / 取还任务、预约窗、司机、签收和超期提醒。 |
| 售后与争议证据散落 | 建立工单和证据包：合同版本、支付流水、交接图、物流、操作审计；设置首响与处理 SLA。 |

## P2：经营增长和合规

| 痛点 | 方案 |
| --- | --- |
| 管理者无法判断资产效率 | 增加利用率、空置天数、租赁取消率、超期率、维修成本、单资产毛利与门店周转仪表盘。 |
| 价格缺乏弹性 | 基于可用库存、淡旺季、租期和提前预订天数配置阶梯价；价格变更保留版本。 |
| 隐私与敏感资料泄露 | KYC 与支付使用第三方 token；业务库只留最小必要字段和脱敏引用；分角色、字段级权限、访问审计、保留期和删除策略。 |
| 平台规模后操作不可追溯 | 引入用户、角色、组织、审计日志、Outbox 事件和通知服务；高风险操作需要双人审核。 |

## 本版数据库设计为什么这样做

租赁排期使用 PostgreSQL `daterange`，租期为 `[start, end)`。范围重叠可以清晰表示，且 `daterange` 的规范形式就是左闭右开；GiST 索引可加速范围重叠查询。因为本业务允许一件商品有多件库存，单一排他约束不能表达“重叠数量总和不得超过库存”，所以最终下单通过商品行锁序列化竞争，并在事务内计算最大同时占用量。

这套组合直接对应 PostgreSQL 对范围、GiST 和排他约束的说明：[Range Types](https://www.postgresql.org/docs/current/rangetypes.html)；行锁用于在并发下协调同一商品的库存判定：[Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)。

## 推荐实施顺序

1. 先稳定当前 P0：商品、库存、客户、租赁 / 销售订单、价格快照、支付流水、状态机和并发测试。
2. 再建设 P1：验机、维修、支付超时、门店库存池、配送取还、实名认证与争议工单。
3. 最后做 P2：动态定价、预测、资产经营 BI、规则引擎和多租户。
